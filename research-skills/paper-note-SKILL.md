# Paper Note 스킬

논문 한 편을 **쉽게 이해되는 한국어 노트 한 장**으로 정리한다. 서베이가 아니다 — `Survey_Guide/`의 커버리지 정책, 완료 게이트, run_validation은 **적용하지 않는다**.

## 절차

1. 논문 원문을 확보한다: arXiv/OpenReview HTML 또는 PDF를 `WebFetch`로 읽는다. 링크가 없으면 `WebSearch`로 공식 소스를 찾는다.
2. `Paper_Notes/<ShortName>.md`로 저장한다.
   - 파일명은 모델/논문 별칭 그대로 (vault 컨벤션과 동일): 예 `GR00T-N1.6.md`, `MemoryVLA.md`, `Cycle-Consistency-Reward.md`
   - 날짜는 파일명이 아니라 frontmatter에 넣는다.
3. 작성 후 관련된 기존 노트가 있으면 `[[]]`로 연결한다 (vault의 `3_Resources/paperarXiv/`, 기존 `Paper_Notes/`, `Survey_Results/` 포함).

## 노트 포맷

```markdown
---
date: {오늘, YYYY-MM-DD}
title: "{논문 원제}"
venue: {학회/저널 또는 arXiv}
year: {발표 연도}
arxiv: {링크}
code: {공식 repo 링크 또는 none}
tags: [paper-note, {분야 태그}]
---

# {ShortName}

> [!quote] TL;DR
> 세 문장 이내. 비유나 직관 우선. "이 논문은 한마디로 ___다."

## 어떤 문제를 푸는가
- 기존 방법이 어디서 막혔는지, 왜 어려운 문제인지를 비전공자도 따라올 수 있게.

## 핵심 아이디어
- 한 문단. 저자들의 한 수가 무엇인지 직관으로 설명. 필요하면 일상 비유.

## 방법 (단계별)
- 입력 → ... → 출력 흐름을 단계별로. 모듈명은 영어 유지.
- 수식은 꼭 필요한 1~2개만 가져오고, 기호를 말로 풀어 설명.
- 표가 그림보다 나을 때는 표 사용.

## 결과는 어땠나
- 핵심 벤치마크 결과 표 1개 (비교 대상의 venue/year 표기).
- 숫자가 의미하는 바를 한두 줄로 해석.

## 한계와 내 생각
- 논문이 인정한 한계 + 읽으면서 든 의문/아이디어를 분리해서.

## See Also
- [[관련 노트]] 링크
```

## 규칙

- 기본 한국어, 기술 용어·모델명·수식 기호는 영어 유지.
- 분량은 기본 1~2페이지. 사용자가 "자세히"라고 하면 늘린다.
- 코드 clone은 하지 않는다. 사용자가 코드 분석까지 원하면 그때 survey 워크플로의 code analysis를 차용한다.
- 확인 못 한 내용은 추측으로 채우지 말고 `[불확실]`로 표시한다.
- 여러 편(2~4편)을 한 번에 요청하면 편당 노트 하나씩 만들고, 비교 요청이 있으면 `Paper_Notes/`에 비교 노트를 하나 더 만든다.
- 5편 이상이거나 "분야를 훑어달라"는 요청이면 survey-research로 전환할지 사용자에게 확인한다.
